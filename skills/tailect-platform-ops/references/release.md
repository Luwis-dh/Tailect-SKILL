# GitHub 与宝塔增量发布

这是一套项目特定流程；实际路径、版本、脚本行为、备份和用户授权以当前环境及仓库部署文档为准。先读 `deploy/record/DEPLOY.md` 和该机器对应的部署账本，再决定交付范围。

## 修改与构建

- 核对 GitHub 的最新提交与本地工作区；线上可能有尚未合入仓库的修复。不能用旧源码镜像覆盖已上线的后端修复。资源文件名或构建哈希不一致并不自动证明源码不一致；结合部署清单、源码、构建环境核验。若基线无法确定，明确风险和选项，尊重用户对继续或暂停的决定。
- 用户要求“只出方案”时不实施；获授权后对症修复，运行与变更相称的测试。前端 `npm run build:record` 包含类型、`/record/` 构建、兼容与路由检查；实际核对脚本配置和输出。
- 遵循项目先提交再出包的约定，确认 Git 提交与产物一致。依据实际变更选择后端、前端或两者，核对构建产物、依赖版本和 SHA-256。若 Docker 构建缓存可疑，按项目手册核对镜像内容。
- 项目完整导出脚本可能依赖 Docker；前端独立构建与打包是可行的技术路径，但必须说明实际方式，不声称执行了未运行的完整脚本。若用户明确要求严格按原脚本执行，无法满足时如实报告，不自行改写约定。

## 上传、更新和保护

- 为每次发布使用新的独立上传目录，校验包和脚本，不与旧包、`docker-compose.yml`、`env.patch` 混放：`update.sh` 会自动识别目录里的包与配置，误放可能触发后端升级或重建。
- 仅前端时使用前端包和脚本；无后端包时脚本跳过后端。显式核对 `WEB_ROOT` 指向目标站点；为避免默认种子单位回填等无关改动，检查实际脚本并在适用时使用 `--no-backfill`。服务器可能允许 SFTP 或宝塔文件上传，依用户要求选用；传完核对 SHA-256。
- 后端升级前检查备份链路、镜像回滚点、依赖、迁移和维护窗口；音频卷和数据库是独立数据，保护二者。不要将“不做功能验收”理解成允许跳过部署前必要的文件完整性和恢复准备。
- `update.sh` 通常先保留旧前端目录，再替换并做基础结构检查；以实际输出确认成功和回滚位置。记录结果并将部署账本按授权提交、推送。不要自动删除回滚包，也不要未经具体授权恢复数据库、清理录音或修改防火墙。
- 如果用户明确自行完成上线功能验证，尊重这一要求；只报告脚本实际结果、未做功能验证和用户可执行的验证方式。明确保留构建基线不确定性，不把脚本完成等同业务验证通过。
